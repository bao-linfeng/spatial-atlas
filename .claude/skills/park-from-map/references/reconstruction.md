# 重建方法：来源分工、精细程度与核验

SKILL.md 和其他 references 讲怎么取数，本文讲取数之外的判断：每类信息以哪个来源为准，做到多细，观察结果怎样落到引擎参数，记录什么，怎样验收。内容来自 02–04 三个园区的实际做法，并吸收了 `创意园3D重建可行性与实施思路.md`（2026-11-01）中可用的部分。

## 1. 目标

目标是展示型的近似重建，不是测绘：能认出园区、主要楼栋、道路和水系，俯视看布局与底图一致，斜视看体量与航拍一致。现行做法能达到下面这些量级，验收时以此为准：

| 项 | 量级 | 依据 |
| --- | --- | --- |
| 截图配准 | 残差 ≤ 2 px（约 1 m） | POI 针尖拟合；创意园 MERC ≤ 1.2 px |
| 平面位置（路口、楼角） | 3–5 m | 高德与百度的楼栋普遍差 3–5 m；主干道吸附前后偏移 ≤ 11 m |
| 岸线 | ≤ 5 m | 创意园水面对卫星图 |
| 核心楼高度 | 高低关系正确，层数 ±1 层 | 百度楼高 + 航拍数层 |
| 周边楼高度 | 高层取百度值；低层归档处理 | 百度低层多为 6–8 m 的默认值 |
| 车流 | `jump` / `hop` / `flip` 均为 0 | `tools/carcheck.js` |

不承诺的内容：真实层高、背立面、屋顶设备的数量和位置、现场最新状况。这些在 `meta.accuracy` / `disclaimer` 里写明。

## 2. 来源分工

| 信息 | 以此为准 | 辅助核对 | 注意 |
| --- | --- | --- | --- |
| 底图坐标 P | 用户给的百度 50 m 比例尺矢量图 | — | 浏览器缩放状态下截的图不当底图，只做配准 |
| 主干道中线 | 手工数字化（百度矢量）后吸附到高德中线 | 卫星图看路口形态 | 高德按道路等级画固定宽度，不能从图上量路宽；两端要伸出沙盘 |
| 支路、绿地、水面、楼栋轮廓 | 高德 19 级整幅截图，按颜色提取 | 百度矢量、卫星图 | 高德常把相邻体量画成一个轮廓，用 `cuts` / `keep` 切开；标准图上的蓝色水面在卫星图上可能是绿色（荷叶），仍按水面处理 |
| 楼高 | 百度矢量瓦片 `building3d` | 航拍数层、全景 | 高层可信；低层的默认值不可信 |
| 屋顶形状、颜色、构架 | 卫星图（百度地球模式） | 航拍 | 高楼倾斜成像（创意园 A 座屋顶向西偏约 20 m）；局部有偏移（大数据园西北角约 15 m）；阴影、树冠 |
| 核心楼的退台、体量组合、幕墙色、标识 | 斜视航拍（用户给的或图库） | 卫星图、全景 | 全景是街面视角，看不到退台顶面和屋顶，这几项要以航拍为准 |
| 核心楼各面外形、立面、层数、首层与入口 | 百度全景，每栋八个方位（见第 6 节） | 航拍补全景拍不到的方位 | 有遮挡、楼顶截断；成本高，只给核心楼做 |
| 楼名、地名 | 地图标注（18 级带标注截图） | POI | POI 只是线索，要结合位置确认是哪栋楼 |
| 高低关系 | — | 地图 3D 模式 | 只用于复核；透视下屏幕上的高度不能当成实际高度 |

冲突时不规定哪个平台总是优先，按对象判断。平面以园区当前的主数据源为准（创意园为高德）。卫星图更能说明问题的就用卫星图，例如大数据园的运河宽度按卫星图水面取。无法判定时，在注释里写明两种来源分别是什么，以及采用了哪一种。

## 3. 范围

- 起点是用户截图，截图里能认出的地标都要落在沙盘内。
- 最终的 `PLATE_PX` 由**路网能否闭合**决定：主干道要在沙盘内串成闭环，或者两端都到沙盘边缘，所以沙盘可以比截图大（创意园向东扩到了龙沧路）。扩大的部分写进 `meta.notes` 的「范围」。
- 范围宁大勿小。之后再扩大的话，要补截图、补瓦片、核对 `at`、重拍基准。

## 4. 精细程度分级

| 等级 | 对象 | 数据 | 建模 | 现有实现（creative） |
| --- | --- | --- | --- | --- |
| 核心 | 园区楼，5–10 栋 | 轮廓逐栋引用，高度按航拍改写 | 分段 `parts`、退台、立面 style、屋顶构件，可点选，带 `info` 文字 | `build/campus.js` 的 `parkBuilding` |
| 核心（无可用轮廓） | 轮廓缺失或被合并得很粗的楼 | 按卫星图量取 `px / w / d / a` | 手写体量 | `F_BLOCKS` / `fBlock` |
| 周边 | 上百栋 | 轮廓挤出，高度取百度值 | 按 house / mid / high 三档配立面和屋面，合并成网格，不参与点选 | `build/context.js` |
| 环境 | 道路、水面、岸线、绿地、树、车 | `data/` 生成 + 主干道手工数字化 | 实例化网格 | `build/roads.js`、`water.js`、`greens.js`、`trees.js` |

重复的楼栋可以共用材质，但要保留观察到的位置、朝向和高度差异。

## 5. 观察结果落到引擎参数

立面由 `core/textures.js` 的 `STYLES` 程序化生成，所以从航拍、全景看到的外观要直接换算成参数，不需要另写自由描述：

| 观察 | 参数 |
| --- | --- |
| 墙面类型 | `style`：`grid` 白色网格框 + 浅灰蓝玻璃；`fin` 深灰玻璃 + 白色竖肋；`ribbon` 白色实墙带 + 横向带窗；`slab` 浅灰墙 + 竖向窗；`villa` 深色玻璃带 + 白楼板线；`punch` 白墙方窗；`amber` 红棕玻璃幕墙；`podium` 玻璃裙房 |
| 层高 | `floorH`（办公默认 4 m，裙房 4–4.5 m，住宅 3.2 m） |
| 层数 | `f`（详情卡片显示）；与 `h` 一致，即 h ≈ f × 层高 + 屋顶 |
| 退台 | `h: [低端, 高端]` + `high`（升高方向上的一点）+ `steps` |
| 一个轮廓里的多段体量 | `cuts` + `keep` |
| 顶部实墙、屋面构架、核心筒、楼顶标识 | `crown`、`frame: { cols, rows }`、`core`、`sign` |
| 屋面颜色 | `roofs.js` 的 `ROOF`：先从卫星图取样，再压暗（场景光照会把浅色明显提亮） |

现有 style 都不贴切时，在 `STYLES` 里新增一种（`punch`、`amber` 都是这样加的），注释写明是为哪栋楼加的。新增 style 只影响用到它的楼，但仍要跑三个园区的回归。

取色：每类材质取多处样本，避开文字、车辆、深阴影、反光和树冠。原始采样色和调整后的颜色都写进注释。阴影交给场景灯光，不烘进贴图。

## 6. 核心楼八方位全景对照

核心楼每栋从八个方位（前、后、左、右，加四个斜角）各取一张百度全景实景图，与模型在同一机位下的截图逐项对照。斜角能同时看到两个面和转角，对判断退台、体量交接、转角处理最有用。

**方位**：按楼本身定。「前」为主入口或主立面朝向，记在该栋的记录里（例如 B 座的前为朝南、带「常州创意」红字的一面）。另外八个方位各记一个罗盘方向（N / NE / E …），便于和地图对照。

**流程**（脚本在 `scripts/`，页面操作细节见 `baidu-web.md`「全景」一节）：

```bash
S=.claude/skills/park-from-map/scripts
# 1. 楼周围的全景点：方位角、距离、拍摄日期（只读元数据接口），存到 .research/pano/near/
node $S/pano-near.mjs --center X,Y --radius 260 > parks/<id>/.research/pano/near/B.json
# 2. 按八方位列候选点，并用楼栋轮廓估算视线遮挡（--at 为楼中心 P 像素，--h 楼高）
node $S/pano-pick.mjs --park <id> --near parks/<id>/.research/pano/near/B.json --at 1437,484 --h 65 --name B
# 3. 每个方位挑一个点，定向截图（--box 为楼中心墨卡托、平面半径 m、取景高度 m）
node $S/pano-capture.mjs --target $T --out parks/<id>/.research/pano --box X,Y,r,H B-前=<全景ID> B-前东角=<全景ID> ...
# 4. 同机位模型截图 + 上下对照图，再拼成总览
node $S/pano-model.mjs --park <id> parks/<id>/.research/pano/B-*.json
node $S/pano-sheet.mjs --out parks/<id>/.research/pano/B-八方位.png parks/<id>/.research/pano/B-{前,前东角,东,后东角,后,后西角,西,前西角}.cmp.png
```

楼中心的墨卡托坐标由 P 反解 `MERC` 得到（`pano-model.mjs` 里有正向换算）。楼高不确定时，`--box` 的 H 取大一些（约 1.5 倍），宁可多留天空也别让楼顶出画。

**选点**：
- 用 `pano-pick` 的候选：方位角在该方位 ±22° 内、距离约 1–2.5 倍楼高（低层楼 40–90 m），遮挡比例接近 0。遮挡只按楼栋轮廓估算，看不出行道树。太近时楼顶会出画，太远时会被树和别的楼挡住。拍摄日期优先选新的。
- 同一方位可以取远近两张：远景看整体轮廓和退台，近景看首层、入口和立面分格。
- 主干道边的点常被行道树挡住（B 座的后、后西角两个方位就是这样），园区内道路的点更清楚。
- 某个方位没有全景覆盖（临河、内院、封闭地块）或被遮挡时，按优先顺序补：同方位的航拍照片 → 相邻方位全景的侧视 → 标「缺」。不要拿别的楼的同类立面去填。

**全景自身的误差**：个别全景点的坐标会偏 10 m 左右，朝向偏几度。B 座试做时 8 个方位里有 2 个对不上，其中一个比例差了一倍。创意园湖西路 2022 年的点有一张整体水平偏了约 20°；F 座内部道路 2017 年的点，标注的距离是 60–80 m，实际离墙只有十几米。所以对照时以多个方位综合判断，单张图对不上时先怀疑全景点，不要据此改平面；必要时换相邻的点重拍验证。偶尔会黑屏（json 里 heading 为 360、pitch 为 0），用 `grep -l '"heading":360,"pitch":0'` 查出来换点重拍。

**不要只看水平方向**：B 座试做时只核对了水平方向的位置和宽度，没注意到同一张图里实景楼顶比模型高得多。每张对照图都要同时看左右位置和楼顶高度。

**每张图记录**：`pano-capture` 写 `<楼id>-<方位>.json`，记全景 ID、坐标、拍摄日期、朝向、俯仰、视场角、截图时间。

**对照项**（逐张填写，汇总写进 `.research/pano/<楼id>.md`；改了模型后，把依据写进 `layout.js` 该栋上方的注释）：

| 项 | 看什么 | 对应参数 |
| --- | --- | --- |
| 外形轮廓 | 天际线、退台级数和方向、体量交接 | `parts`、`cuts`、`h`、`high`、`steps` |
| 层数 | 窗带重复数，首层、设备层是否特殊 | `f`、`h`、`floorH` |
| 立面 | 实墙与玻璃的比例、横向或竖向分格、框料颜色 | `style`，必要时新增 style |
| 颜色 | 主墙、玻璃、框料（取向光面和背光面综合判断） | style 内配色、`M.white` 等 |
| 顶部 | 实墙收头、构架、机房、标识 | `crown`、`frame`、`core`、`sign` |
| 首层与附属 | 入口雨棚、连廊、裙房、架空层 | 目前没有对应参数，按需新增 |

八个方位都对照过的面才算「已观察」；只有一个方位看到的写「（全景 <方位>）」；没有任何实景依据的面沿用同栋可见面，标「（估）」。

## 7. 高度

按顺序处理：

1. 百度 `building3d` 楼高，按高德轮廓在 ±8 m 内平移匹配（`buildings.mjs`）。**这个值对高层可能明显偏低**：创意园 A–E 座实际都在 22–27 层（约 90–110 m），百度给的是 62–81 m（A 座 62 m 分到 25 层，每层只有 2.5 m，不可能）。偏低的比例各栋不同（约 1.25–1.6 倍），不是单位换算出错，不能统一乘系数。
2. 核心楼：数窗带层数 × 层高，与百度值互相核对，采用值写进 `h`，层数写进 `f`。层数可以从全景里数：用 `pano-capture` 把 `--box` 的 H 取大（约 150 m）、`@75` 补拍一张楼顶入画的视角，再裁出塔身放大来数（ffmpeg `crop` / `scale`，见 `.research/pano/height/*-层数.png`）。数层数不受全景点坐标和俯仰误差的影响。
3. 按楼顶仰角反算只作旁证：仰角 = pitch + atan((屏幕中心行 − 楼顶行) / f)，f = 半屏高 / tan(fov / 2)；离楼的距离取同一张图里模型楼顶的仰角和模型高度来推。离楼近、仰角超过 50° 时误差会大到失去意义（创意园 E 座算出 117–179 m）。
4. 首层、裙房、被树挡住的部分，用八方位全景补（第 6 节）。看不全的记下「可见 n 层」，不硬凑完整层数。
5. 用地图 3D 模式复核整片区域的高低关系。全景里也能顺带看出周边楼是否同样偏低（创意园 E 座东侧一栋住宅高层，实景约为模型的 1.3 倍）。

明显冲突时，先查是不是匹配错了楼（平移匹配会配错相邻楼）、影像年代是否不同、层数是否数错，不要直接取平均。低于 8 m 的百度值视为默认值，按 3 层 9.6 m 处理。改进办法见第 12 节。

## 8. 记录

不单独建每栋楼的观察表，记录放在数据旁边：

| 记什么 | 写在哪 |
| --- | --- |
| 截图配准：控制点、残差 | `tools/reg.js` 注释；网页截图的元数据由 `capture.mjs` 写成同名 json |
| 生成数据的来源与生成方式 | `data/*.js` 文件头（「请勿手改」） |
| 每个手写常量的依据 | `layout.js` 注释：取自哪张图（航拍写编号）、哪个工具、什么参数 |
| 整园区的来源与精度说明 | `park.js` 的 `meta.sources`、`accuracy`、`disclaimer` |

可信程度按字段区分，不给整栋楼一个笼统的等级（平面确认了，不代表高度也确认了）。注释用统一的词：

- 不加标注：有清晰视图直接支持；
- 「（百度）」「（航拍 VCG…）」：注明来源；
- 「（估）」：依赖假设，例如层高、看不见的立面；
- 「待核实」：信息不足，或几个来源冲突且未解决。

核心楼遇到冲突、推测较多时，在该栋 `layout.js` 条目上方写一段注释，依次交代轮廓来源、高度来源、层数、立面依据和推测部分。影像年代能确认的（图库航拍通常有拍摄日期）写在 `meta.sources`，不能确认的就不写。截图元数据里不要存 token、cookie 一类凭证。

## 9. 实施顺序

1. **范围、底图、配准**：用 `crop.html?...&layout` 叠加核对后再往下走。配准错了，后面的所有数据都会跟着错。
2. **样区试做**：挑一栋核心楼、一段主干道、一段岸线，走一遍截图 → 提取 → 白模 → 对照航拍。顺便评估截图细节是否够用、全景覆盖如何（百度全景路线只覆盖部分道路）、人工修正要花多少工夫。样区做成了，不代表其他楼栋的资料也同样齐全。
3. **主干道与车流**：先让车流检查为 0，再铺支路。
4. **生成 `data/`**：楼栋、支路、绿地、水面。
5. **白模核对**：俯视对底图，斜视对航拍（页面上的「白模」按钮）。
6. **细化**：核心楼 → 周边 → 材质 → 树、车、路灯。
7. **收尾**：标注、导览、夜景，同步文档（`integration.md`），建立回归基准。

每一步通过核对后再进入下一步，免得在错误的轮廓上叠细节（创意园从百度换到高德时，园区楼的 `at` 和切分都重做了一遍）。

## 10. 验收

| 项 | 方法 | 通过条件 |
| --- | --- | --- |
| 配准 | `crop.html?...&layout` 叠加 | 残差 ≤ 2 px，没有系统性漂移，记录在 `reg.js` |
| 平面 | `tools/shot.html` 俯视，对照底图和高德 | 核心楼的轮廓、朝向、间距一致；没有道路穿楼 |
| 体量 | 用与航拍相近的机位截图对照 | 高低关系、退台方向、塔楼与裙房的组合一致 |
| 外观 | 核心楼八方位：全景实景与同机位模型截图并排 | 每个方位的轮廓、退台、层数、主色、窗带、标识与实景一致；缺的方位已注明 |
| 道路 | 俯视 + `tools/jump.html` | 沙盘内没有断头的主干道，桥面连续，三类车流异常为 0 |
| 水系 | 俯视对照卫星图 | 岸线差 ≤ 5 m，半岛和岛保留，树不落在水里 |
| 材质 | 白天光照下看 | 没有残留标注色，没有烘进去的阴影 |
| 可追溯 | 抽查 `layout.js` 注释和 `meta` | 每个采用值都有来源，或标了「（估）」 |
| 回归 | `tools/regress.mjs` | 纯重构必须通过；有意改变画面时用 `--update`，并在提交信息里说明 |
| 文档 | 对照 `meta`、`parks/index.js`、README、CLAUDE.md | 栋数、指标、范围描述一致 |

## 11. 使用边界

- 截图和页面缓存只用于本项目的示意性重建，不批量下载瓦片后脱离地图服务使用。
- 仓库公开或对外发布前，核对高德、百度的服务条款，以及 `docs/` 里航拍照片的授权。视觉中国是商业图库，`VCG*.jpg` 只适合作内部参考，不能随仓库公开。
- CDP 只在自己新建的后台标签页里操作，结束时关闭（见 `baidu-web.md`）。
